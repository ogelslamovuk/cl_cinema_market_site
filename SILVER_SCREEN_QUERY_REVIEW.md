# Silver Screen: черновик выгрузки для проверки заказчиком

Статус: **согласован для PoC и выполняется только read-only с явным диапазоном дат**.

Файл запроса: `sql/silver_screen_market_export.sql`.

## Ожидаемый результат

Запрос возвращает одну строку на один сеанс Silver Screen и позволяет далее агрегировать данные:

- по дате сеанса;
- по прокатной неделе с четверга по среду;
- по кинотеатру;
- по городу и области;
- по фильму;
- по залу и времени начала;
- по типам операций 1 и 2, а также по их нетто-результату.

Выгружаются количество билетов, `grossSum`, `priceSum`, `bonusSum` и количество транзакций. В запрос попадают и сеансы без продаж, чтобы отличать нулевой результат от отсутствующей строки.

## На чём основан запрос

Использованы только локальные материалы `D:\JetBrains\DB\SS_DataBase`:

1. `SS_DATABASE_SKILL.md` и `PROJECT_INSTRUCTIONS_FOR_CHATGPT.md` — правила read-only и запрет придумывать бизнес-логику.
2. `schema/schema.sql`, процедура `reports.collect_dashboard_data` — существующий производственный паттерн для билетов:
   - `reports.sales.mode = 0`;
   - `reports.sales.product = cinema.show.id`;
   - учитываются `reports.sales.type IN (1, 2)`;
   - день показа определяется через `cinema.show.AccountingDate`;
   - количество считается как сумма `reports.sales.quantity`;
   - касса считается как сумма `reports.sales.grossSum`.
3. Подтверждённые FK из `schema/relations.csv`:
   - `cinema.show.Event -> cinema.events.id`;
   - `cinema.show.Theater -> global.theaters.id`;
   - `cinema.show.Auditorium -> cinema.auditoriums.id`;
   - `global.contactinformation.OwnerTheaters -> global.theaters.id`;
   - `global.contactinformation.City -> global.city.id`;
   - `global.city.Region -> global.region.id`.

Процедура была использована только как документация существующей логики. Никакие `CALL`, DDL или DML в черновик не перенесены.

## Допущения, которые должен подтвердить заказчик

1. **Дата сеанса.** Основной день отчёта — `cinema.show.AccountingDate`, поскольку именно так считает существующий сборщик dashboard. Одновременно выгружается `DATE(cinema.show.Start)` для контроля расхождений около полуночи.
2. **Фильм.** Бизнес-название фильма берётся из `cinema.events.Name`, идентификатор — `cinema.show.Event`.
3. **Сеанс.** Уникальный ключ сеанса — `cinema.show.id`.
4. **Вместимость.** Вместимость зала берётся из `cinema.auditoriums.SeatsCount`. Поле `cinema.show.seatsCount` в текущем запросе не используется; нужно подтвердить, какое из них является правильным для исторического сеанса.
5. **География.** Город кинотеатра берётся через `global.contactinformation`. Если у кинотеатра найдено несколько разных городов, запрос детерминированно выбирает запись с минимальным `city_id` и возвращает `geography_candidate_count > 1` как признак проблемы. После первой согласованной проверки такие случаи должны быть разобраны вручную.
6. **Прокатная неделя.** `release_week_start_thursday` — четверг, к которому относится `AccountingDate`; интервал недели считается `[четверг; следующий четверг)`.
7. **Неактивные сеансы.** Запрос намеренно не фильтрует `cinema.show.Active`: отменённые или выключенные сеансы могут содержать возвраты и должны оставаться видимыми. Правило исключения таких сеансов из KPI нужно согласовать отдельно.

## Критически неизвестная бизнес-логика

В `docs/open_questions.md` прямо указано, что справочник статусов продаж и возвратов пока не описан. Поэтому запрос **не называет**:

- `reports.sales.type = 1` продажей;
- `reports.sales.type = 2` возвратом.

Он выводит их раздельно как `operation_type_1_*` и `operation_type_2_*`, а также выводит сумму обоих типов как `net_*`. Перед подключением к продуктовым метрикам заказчик должен подтвердить:

1. какой тип означает продажу, какой — возврат и существуют ли иные релевантные типы;
2. являются ли `quantity`, `grossSum`, `priceSum` и `bonusSum` в возвратных строках отрицательными либо их нужно инвертировать;
3. что именно является кассой для доли рынка: `grossSum`, `priceSum`, `grossSum - bonusSum` или другой проверенный показатель;
4. включаются ли в `grossSum` скидки, сертификаты, бонусы и комиссии;
5. надо ли считать билетами только уникальные `ticket` либо корректной метрикой остаётся `SUM(quantity)`, как в существующем `collect_dashboard_data`;
6. должны ли аннулирования, технические операции и повторно сформированные чеки исключаться дополнительным условием.

До этих ответов нельзя переименовывать поля в `sold_tickets`, `refund_tickets` и `revenue`.

## Почему запрос нельзя выполнять без подтверждения

Заказчик явно установил правило: любые обращения к Silver Screen DB разрешены только после проверки и согласования конкретного query. Кроме того, без подтверждения семантики типов и знаков можно получить внешне правдоподобную, но неверную посещаемость и долю рынка.

Для безопасной проверки сначала следует согласовать текст SQL, затем отдельно согласовать минимальный диапазон одной даты и ожидаемые контрольные итоги. Настоящий файл сам по себе ничего не выполняет и не содержит подключения к базе.

## Предлагаемые контрольные проверки после разрешения заказчика

Эти проверки описывают будущую приёмку и сейчас не выполнялись:

1. Сверить итог `SUM(net_ticket_quantity)` за один известный день с утверждённым отчётом Silver Screen.
2. Сверить `SUM(net_gross_amount)` за тот же день.
3. Проверить по одному сеансу с продажами без возвратов и по одному сеансу с частичным возвратом.
4. Найти расхождения `accounting_date <> session_calendar_date`.
5. Проверить строки с `geography_candidate_count <> 1`.
6. Проверить сеансы с отрицательными нетто-значениями и сеансы, где нет операций.
7. После подтверждения семантики переименовать технические поля типов в продуктовые названия без изменения исходного слоя.
