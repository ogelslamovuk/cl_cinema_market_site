# Исследование API 24afisha

Дата проверки: 31 июля 2026 года.

Дополнительное обследование всей Беларуси: 3 августа 2026 года.

## Краткий вывод

API позволяет автоматически получить расписание киносеансов, `sid`, точное время закрытия онлайн-продаж, кинотеатр, фильм, зал и состояние мест.

Для большинства проверенных кинотеатров API дополнительно возвращает:

- `sellsCount.count` — количество проданных билетов;
- `sellsCount.sum` — сумма продаж в копейках;
- `reservedCount.count` — количество забронированных/удерживаемых мест;
- `reservedCount.sum` — их сумма в копейках.

Для внешних интеграций (на момент проверки Falcon Club, SKYLINE и Prizma) этих агрегатов нет. Там доступны состояния отдельных мест `available` и `reserved`, поэтому можно точно считать свободные и недоступные места, но не всегда можно отделить продажу от технической блокировки.

Исторические данные после stop-sale обычно недоступны. Сеанс нужно опрашивать до `timeSpendingStopsale` и сохранять последний успешный снимок.

## Защита API

Обычный первый HTTP-запрос возвращает не JSON, а HTML `Verification`.

Ответ содержит:

- cookie `hg-client-security` в заголовке `Set-Cookie`;
- значение cookie `hg-security` непосредственно в JavaScript страницы;
- `hg-security` имеет `max-age=120`.

Для чистого HTTP-клиента достаточно:

1. Выполнить исходный запрос с cookie-session.
2. Если пришёл HTML Verification, извлечь `hg-security=...` из тела.
3. Установить эту cookie для `api.24afisha.by`, сохранив выданную сервером `hg-client-security`.
4. Повторить запрос.
5. При повторном челлендже обновить cookie и повторить операцию один раз.

Вычислять JavaScript и запускать Chromium не требуется.

## Endpoints

### Список фильмов на дату

```text
GET /api/v3/mobile/afisha/kino
    ?date={local_midnight_unix}
    &ignoreEndTime=1
    &cityId=3
    &lang=ru
    &onlyData=0
```

Полезные поля:

- `data.currentDate[]` — фильмы;
- `data.currentDate[].id` — `performance_id`;
- `data.currentDate[].name` — название;
- `objects[]` — список площадок для фильтра интерфейса, но он не является полным источником расписания.

### Расписание конкретного фильма

```text
GET /api/v2/schedule/events/{performance_id}
    ?cityId=3
    &lang=ru
    &slug=true
    &jsonld=0
    &time={local_midnight_unix}
```

Структура:

```text
data[]                     фильм
  objects[]                кинотеатры
    sessions[]             сеансы
```

Поля сеанса:

- `id` — публичный `sid`;
- `timeSpending` — начало сеанса;
- `timeSpendingStopsale` — закрытие онлайн-продаж;
- `isSaleOpen`;
- `isBooking`;
- `objectId`;
- `outerSessionId`;
- `minPrice`, `maxPrice`;
- `timezone`;
- `tags`.

Этот endpoint является надёжным способом первичного обнаружения всех кинотеатров и сеансов, включая SKYLINE.

### Расписание известного кинотеатра

```text
GET /api/v2/schedule/objects/{object_id}
    ?lang=ru
    &cityId=3
    &jsonld=0
    &time={local_midnight_unix}
```

Структура:

```text
data[]
  events[]
    sessions[]
```

После формирования справочника конкурентов этот endpoint выгоднее: один запрос на кинотеатр возвращает все его сеансы за выбранную дату.

Проверенные примеры на 1 августа 2026 года:

- `object_id=5180`, SKYLINE Cinema тц Galileo — 37 сеансов;
- `object_id=5359`, Prizma cinema — 14;
- `object_id=92`, Falcon Club — 30;
- `object_id=104`, «Салют» — 4.

### Инициализация виджета сеанса

```text
GET /api/v3/frame/init?sid={sid}&lang=ru
```

`distributor_company_id=296` не является паролем и для чтения проверенных данных не обязателен. Это идентификатор канала/дистрибьютора. Результаты без параметра, с `296` и с другим ID совпали.

Полезные данные:

- `session` — начало, stop-sale, флаги продажи;
- `object` — кинотеатр;
- `performance` — фильм;
- `mapData.map.id` — ID схемы зала;
- `mapData.map.hallName` — название зала;
- `mapData.map.type` — `places`, `placesSection` или `dances`;
- `mapData.map.sections[]` — секции и предварительные агрегаты.

Предварительным `placesAvailable/placesFree` нельзя безусловно доверять. У внешних интеграций они могут быть заглушками (например, 664/664 при фактических 143 креслах).

### Детальные места

```text
GET /api/v2/frame/session/{sid}/map/section/{section_id}/places/slim/?lang=ru
```

`schema` декодирует компактные массивы/объекты `data`:

```text
id, x, y, type, row, place, sectionId, available, reserved,
zoneId, color, withPlacesArray, orderId, companyId, ...
```

Для подсчёта кресел нужно учитывать элементы `type == 0`. Остальные элементы — экран, подписи и графические объекты схемы.

Для внутренней интеграции ответ содержит:

- `legend.placesCount`;
- `legend.placesFree`;
- `sellsCount`;
- `reservedCount`;
- `cached_at`;
- `zonePrices`.

Проверенная инварианта:

```text
placesCount - placesFree = sellsCount.count + reservedCount.count
```

Она сошлась на всех пяти активных сеансах, использованных для проверки.

Для внешней интеграции `sellsCount`, `reservedCount` и `legend` могут отсутствовать. Тогда считаются:

```text
capacity = count(type == 0)
free = count(type == 0 and available == true)
unavailable = count(type == 0 and available == false)
reserved_visible = count(type == 0 and reserved == true)
```

В исходном API `unavailable` технически не разделён на продажи и внутренние
удержания. Для продуктовой аналитики заказчик утвердил единое бизнес-правило:
`Admissions = capacity - free`; `reserved=true` дополнительно не вычитается.

### Безместная/входная зона

```text
GET /api/v2/frame/session/{sid}/map/dances
```

Возвращает зоны с `placesAvailable`, `placesFree`, `placesSell` и тарифами. Этот тип нужно обрабатывать отдельно от кресельной схемы.

### `/api/v3/frame/data`

```text
GET /api/v3/frame/data
```

Endpoint полезен как оперативный поток и fallback, но не как полное расписание дня.

Во время проверки он стабильно возвращал ровно 100 ближайших/текущих записей одной даты. Параметры `date`, `time`, `cityId`, `limit`, `page`, `offset` и `distributor_company_id` не меняли результат. В выдаче смешаны кино и другие билетные события по разным городам.

Его можно использовать для:

- контроля появления новых `sid`;
- восстановления части пропущенного расписания;
- диагностики API.

Для планирования полного дневного сбора нужны `/schedule/events` или `/schedule/objects`.

### Публичная Swagger-схема и поток `/api/v1/frame/session`

```text
GET https://api.24afisha.by/docs
```

Endpoint возвращает Swagger 2.0 для старого `basePath=/api/v1`: 99 описанных
маршрутов. Это полезная документация поведения v1, но не полный контракт
фактически используемых v2/v3.

В схеме найден публичный пагинированный поток:

```text
GET /api/v1/frame/session
    ?page=1
    &per-page=1000
    &expand=performance,institution
```

Он возвращает текущие сеансы в продаже, отсортированные по времени, вместе с
`performance`, `institution`, map ID, началом и stop-sale. На момент проверки в
потоке было 5814 сеансов всех типов событий. На 4 августа в первой странице
оказалось 564 сеанса:

- 506 киносеансов с `institution.objectTypeId=2`;
- 56 событий типа 13;
- по одному событию типов 1 и 20.

Сопоставление с `/api/v2/schedule/objects/{id}` на ту же дату:

- основной discovery: 507 киносеансов;
- v1 sale stream: 506;
- пересечение: 505;
- объединение: 508.

Один сеанс нашёлся только в sale stream, два — только в расписании и имели
`isSell=false`. Поэтому v1 подключён как независимый reconciliation/fallback,
а не как единственный источник.

Ограничения v1 sale stream:

- исчезнувшие из продажи сеансы не образуют исторический архив;
- `from`, `to`, `only` и `timeSpending` в проверенном list endpoint не меняли
  результат;
- варианты `filter` JSON и `filter[field]` давали HTTP 500;
- поэтому поток нужно читать постранично до временного горизонта, а кино и даты
  фильтровать на стороне сборщика;
- агрегатов `sellsCount` в карточке `/api/v1/frame/session/{sid}` нет.

`/api/v1/frame/performance/{id}/sessions` принимает `from`/`to` и может быть
fallback для конкретного фильма. `/api/v1/buffer/session` без авторизации вернул
HTTP 401.

Swagger также описывает операции с заказами и сканированием билетов. Они
относятся к привилегированному операционному контуру, могут содержать
персональные/заказные данные и для этой аналитики не используются. Отсутствие
корректных security-аннотаций в старой Swagger-схеме не означает публичность
таких данных.

## Алгоритм сбора

### Discovery

1. Получить справочник городов и республиканский каталог кинообъектов.
2. Для каждого объекта запросить `/schedule/objects/{object_id}` на текущий
   временной горизонт.
3. Сохранить кинотеатры, фильмы и сеансы с уникальным `sid`.
4. Объединить результат с текущим v1 sale stream, сохранив lineage обоих
   источников.
5. Полный object discovery выполнять примерно раз в 6 часов.
6. Между полными проходами каждые 30 минут сверять лёгкий пагинированный
   `/api/v1/frame/session`: расписание может дополняться или изменяться.
7. Новые/изменённые сеансы планировать заново идемпотентно.

### Snapshot

Планировать измерение относительно `timeSpendingStopsale`, не относительно начала сеанса.

Рекомендуемый режим:

- первый снимок за 3 минуты до stop-sale;
- повтор за 60 секунд;
- финальный снимок в пределах 20 секунд до stop-sale;
- `cached_at` хранить как QC-метаданные, но не отбрасывать из-за его возраста
  арифметически согласованный снимок в финальном окне;
- сохранить последний успешный ответ;
- после закрытия не затирать успешный снимок пустым ответом.

Закрытые исторические карты нельзя массово опрашивать в том же пуле, что и
live-сеансы: медленные timeout backlog блокируют актуальные stop-sale. После
grace-зоны результат фиксируется как `best_available` или `missed_window`.

Если источник кеширует данные, сохранять одновременно:

- локальный `observed_at`;
- серверный `cached_at`;
- рассчитанный возраст кеша.

Для аномально раннего stop-sale делать попытку сразу после discovery и присваивать явный статус, если окно уже потеряно.

### Классификация качества

- `exact_api_sales` — присутствуют `sellsCount` и `reservedCount`;
- `availability_estimate` — доступны только `available/reserved` по местам;
- `general_admission` — карта типа `dances`;
- `closed_before_capture` — endpoint закрылся до первого успешного снимка;
- `source_anomaly` — некорректное время или противоречивые агрегаты;
- `capture_failed` — сетевой/форматный сбой после повторов.
- `missed_window` — окно stop-sale прошло без пригодного снимка;
- `expired_unobserved` — сеанс старше окна восстановления и никогда не наблюдался.

## Вместимость залов

Идея кешировать вместимость правильная, но считать её один раз навсегда опасно.

Надёжный вариант:

1. Декодировать детальную карту.
2. Считать кресла как `type == 0`.
3. Строить нормализованный fingerprint из ID мест, рядов, номеров, секций и `withPlacesArray`.
4. Кешировать layout по `(cinema_id, source_map_id, fingerprint)`.
5. При изменении fingerprint создавать новую версию схемы.
6. Периодически перепроверять карту, даже если `map_id` прежний.

`map.id` может повторяться в разных кинотеатрах, поэтому он не является глобальным ключом.

Для внешних интеграций стоит сохранять seat-level снимки хотя бы в сжатом виде. Пересечение постоянно недоступных seat ID на множестве будущих сеансов позволит выделить вероятные технически заблокированные места и улучшить оценку продаж.

## Риски

- API не обещает стабильность формата и версионирование поведения.
- Закрытый сеанс нельзя надёжно восстановить задним числом.
- Внешняя интеграция не гарантирует разделение sold/blocked/held.
- Расписание может добавляться и изменяться в течение дня.
- `placesAvailable` из `frame/init` может быть заглушкой.
- Времена stop-sale могут содержать аномалии.
- Значения денег хранятся в minor units: `1700` означает `17.00 BYN`.
- Полученные показатели — данные публичного ticketing API, а не бухгалтерский отчёт организатора.

### Наблюдаемое ограничение нагрузки

Во время локального stress/backlog-теста после серии параллельных запросов API
начал отвечать read timeout даже на одиночный `/api/v2/cities`. Это может быть
защитное ограничение по IP либо временная деградация сервиса; HTTP 429 источник
не вернул.

Поэтому production-настройки консервативны:

- исторический backlog карт не опрашивается;
- одновременно работают не более двух capture-worker'ов;
- capture timeout короткий, без немедленного retry;
- при полном отказе включается экспоненциальная пауза;
- тяжёлый discovery использует timeout 12 секунд без retry и прерывается после
  пяти последовательных ошибок;
- полный discovery выполняется раз в 6 часов, лёгкий sale reconciliation — раз
  в 30 минут.

## Обследование всей Беларуси 3 августа 2026 года

Проверка выполнена чистыми HTTP-запросами, без Chromium и без графического браузера.
Исходный машинный отчёт формируется командой:

```text
python probe_api.py --date 2026-08-04
```

### Каталоги

```text
GET /api/v2/cities?lang=ru
```

Возвращает 35 городов. Для каждого города доступны:

- `id`, `name`, `slug`;
- `regionId` и вложенный `region` с названием области;
- координаты и timezone.

```text
GET /api/v3/pages/objects
    ?filter[typeIds]=2
    &filter[perPage]=100
    &jsonld=1
```

Без `cityId` endpoint возвращает республиканский каталог: 113 объектов типа
«кинотеатр». Не все объекты имеют сеансы на выбранную дату. Каталог нужно
использовать для discovery, а активность определять по расписанию.

### Полнота расписания на 4 августа 2026 года

- 35 городов в справочнике;
- 113 кинообъектов в каталоге;
- 51 кинотеатр с сеансами;
- 26 городов с активным расписанием;
- 507 сеансов;
- 507 уникальных `sid`;
- дублей `sid` нет;
- ошибок получения расписания нет;
- все 507 времён начала попали именно на запрошенную локальную дату.

`/api/v2/schedule/objects/{object_id}` работает без обязательного `cityId`.
Это позволяет строить полный республиканский discovery одним каталогом объектов
и одним запросом расписания на активный объект/дату.

### Stop-sale по 507 сеансам

`timeSpendingStopsale` нельзя выводить из времени начала по фиксированному правилу.
Фактический диапазон смещения составил от -270 до +120 минут:

- до начала сеанса закрывались 112 продаж;
- ровно в момент начала — 376;
- после начала — 19.

Следовательно, снимок нужно всегда планировать по фактическому
`timeSpendingStopsale`. Допущение «продажи всегда закрываются перед началом»
неверно.

### Классификация по одному сеансу каждого активного кинотеатра

Из 51 активного кинотеатра:

- 47 вернули точные `sellsCount` и `reservedCount`;
- SKYLINE Cinema, Prizma cinema и Falcon Club вернули только состояния мест;
- Синемариум использует `dances`/general admission.

Для всех 47 точных интеграций проверка

```text
placesCount - placesFree = sellsCount.count + reservedCount.count
```

прошла без единого расхождения.

Проверенные внешние интеграции:

| Кинотеатр | Зал | Вместимость | Свободно | Недоступно | `reserved=true` |
|---|---|---:|---:|---:|---:|
| SKYLINE Cinema | 5 | 143 | 132 | 11 | 0 |
| Prizma cinema | 2 | 101 | 99 | 2 | 0 |
| Falcon Club | Love Seats | 9 | 3 | 6 | 6 |

У недоступных мест SKYLINE и Prizma отсутствовали публичные `orderId`,
`companyId` или другой надёжный признак продажи. Поэтому недоступность нельзя
автоматически приравнять к проданному билету.

General admission Синемариума возвращается массивом, а не JSON-объектом. В
проверенном ответе одновременно присутствовали `placesAvailable=500`,
`placesFree=6` и `placesSell=0`. Смысл этих полей нельзя считать доказанным по
одному ответу; для этого источника требуется временной ряд и отдельная проверка.

### Проверка исторического восстановления

Тот же республиканский discovery для 2 августа 2026 года вернул только 3 сеанса
в 3 кинотеатрах. Для сравнения, будущая дата 4 августа вернула 507 сеансов.

Вывод: schedule API не является историческим архивом. Даже если отдельный
`frame/init` некоторое время продолжает отдавать кеш закрытого сеанса, это нельзя
использовать как стратегию восстановления прошедшего дня. Сборщик должен работать
непрерывно и сохранять результат самостоятельно.

## Контракт данных для продукта

### Можно использовать как точные данные

- `sid`, кинотеатр, город и область;
- фильм и `performance_id`;
- начало сеанса и фактический stop-sale;
- зал, map ID/type, расписание и ценовой диапазон;
- `sellsCount.count` и `sellsCount.sum`, когда поля присутствуют;
- `reservedCount.count` и `reservedCount.sum` отдельно от продаж;
- вместимость и свободные места при согласованной детальной карте;
- серверный `cached_at` вместе с локальным временем наблюдения;
- `placesSell` для general admission только после отдельной валидации.

### Можно использовать только как оценку

- продажи SKYLINE, Prizma и Falcon Club как изменение/недоступность мест;
- их кассу как диапазон по тарифам зон;
- технически заблокированные места после накопления повторяющегося baseline по
  одному hall layout;
- продажи general admission после проверки динамики его полей на нескольких
  сеансах.

Любая оценка должна храниться отдельно от точного значения и иметь `quality_mode`.

### API не даёт

- бухгалтерские отчёты кинотеатров;
- историю продаж по завершившимся дням;
- список заказов и покупателей;
- точную причину недоступности места во внешней интеграции;
- гарантированную фактическую цену покупки со скидкой во внешней интеграции;
- подтверждение прохода зрителя через билетный контроль;
- стабильный SLA или версионированный контракт формата;
- готовую долю рынка или отчёт по выручке.

### Рекомендуемые продуктовые показатели качества

- доля сеансов, снятых до stop-sale;
- доля билетов с `exact_api_sales`;
- доля рынка, рассчитанная оценочно;
- число `closed_before_capture`, `capture_failed` и `source_anomaly`;
- возраст кеша на финальном снимке;
- полнота кинотеатров и сеансов против discovery;
- отдельные точная и оценочная касса.
